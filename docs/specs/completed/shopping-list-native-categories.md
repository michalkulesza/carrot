## Context

Revise the mobile shopping-list experience so adding and completing items feels fluid, native, and enjoyable; organize items into user-configurable shopping categories; and provide Gemini with those categories during ingredient extraction so recipe-derived additions land in the correct section. The implementation will add the approved execution plan to `docs/specs/` during execution.

## Approach

### 1. Establish the category contracts and migrate persisted data

1. Copy this approved specification to `docs/specs/shopping-list-native-categories.md` before implementation so the repository carries the pending plan required by the project rules.
2. Add the shared TypeScript catalog to `packages/shared/src/types.ts`: `ShoppingCategory = 'produce' | 'pantry' | 'dairy_eggs' | 'meat_seafood' | 'frozen' | 'other'` and the ordered default `['produce', 'pantry', 'dairy_eggs', 'meat_seafood', 'frozen', 'other']`. Reuse that type in `ShoppingListItem`, recipe ingredient/component save types, API request types, and all mobile category helpers; do not introduce display strings into persisted data.
3. Extend `ShoppingListItem` in `services/api/src/api/models.py` with `category: ShoppingCategory`, persisted as `VARCHAR(32) NOT NULL DEFAULT 'other'`. Extend `UserPreferences` with `shopping_categories: list[ShoppingCategory]` (the enabled IDs in display order; default all six) and `show_completed_shopping_items: bool` (default `False`). Add matching output/update schemas, including validation that removes duplicates, rejects unknown IDs, and always retains `other`; keep category expansion state out of the API because it is device-local.
4. Add idempotent `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` startup migration statements in `services/api/src/api/main.py`, following the current preference-column migration block. Existing list rows start as `other`; existing users receive the complete default ordered catalog.
5. Change the client/server shopping contracts cleanly:
   - `POST /api/shopping-list` body becomes `{"items":[{"text": string,"category": ShoppingCategory}]}`. Additions append to the last incomplete item in their own category, not a global position.
   - `PATCH /api/shopping-list/order` body becomes `{"category_orders": {"produce":[uuid], ...}}`, where every active item ID appears exactly once under its resulting stored category. The route validates the complete active-item ID set, updates category and zero-based position atomically, then publishes one SSE snapshot. A duplicate, missing, foreign, or completed ID returns 422 without a partial change.
   - Keep `PATCH /api/shopping-list/{id}` for text/completion only. All category changes, including cross-category dragging, use the order endpoint; completion retains category and assigns the next position within that category’s destination completion state.
   - Preserve global `DELETE /completed`, edit locking, and SSE behavior. Update `packages/shared/src/api/client.ts` and `useShoppingList.ts` signatures to use `ShoppingListItemInput { text: string; category: ShoppingCategory }` and the category-order payload; remove the obsolete string-array/global-order path and migrate every callsite found in `apps/mobile/src/screens/ShoppingListScreen/index.tsx` and `apps/mobile/src/screens/RecipeDetailScreen/index.tsx`.
6. Keep optimistic cache behavior, but build temporary items with their requested category and category-local position. Put add, toggle, and reorder requests behind one per-hook FIFO write queue: each action updates the cache immediately, then waits for the prior write before issuing its API request. Roll back only the failed action’s snapshot, and invalidate after the queue drains so an older response cannot overwrite a newer optimistic state.

### 2. Carry categories through recipe extraction and manual recipe editing

1. Extend the Python `Ingredient`, `EnrichmentComponent`, `RecipeEnrichment`, and assembled recipe contract in `services/api/src/api/models.py` / `services/api/src/api/services/gemini.py` with a category value parallel to every `shopping_list_value`. Gemini’s enrichment system prompt must receive the fixed six-ID catalog with concise English meanings and return exactly one valid ID per source ingredient in `shopping_list_categories`; it must not use localized display strings or invent IDs.
2. Update `_repair_enrichment_alignment` and `assemble_recipe` so an absent/misaligned category list is repaired to `other` for only the bad entries, while valid sibling results survive. Persist the aligned category values in each recipe component as `shopping_list_categories`, parallel to `ingredients` and `shopping_list_ingredients`, in `services/api/src/api/services/import_worker.py`.
3. Update all editable recipe component shapes and transformations — `apps/mobile/src/screens/NewRecipeScreen/helpers.ts`, `RecipeFormView.tsx`, `apps/mobile/src/screens/RecipeDetailScreen/helpers.ts`, `useEditDraft.ts`, `EditView.tsx`, and `packages/shared/src/types.ts` — so adding, changing, removing, filtering, saving, or restoring an ingredient keeps `shopping_list_categories` aligned with its ingredients. New manual ingredients default to `other`.
4. Add a compact category control to each editable ingredient row in both recipe create and recipe-detail edit flows. It uses `ActionSheetIOS` with the six translated category labels; selection changes only that recipe ingredient’s stored category. Do not build a custom picker when the native action sheet already fits the choice.
5. Update `ComponentSection.tsx`, `UnifiedIngredientsSection.tsx`, `ReadView.tsx`, and `RecipeDetailScreen/index.tsx` so single and “add all” recipe actions pass `{ text, category }` pairs to `addItems`. Preserve an ingredient’s category through the existing text-confirmation sheet; a later shopping-list drag changes only the created list item, never the recipe source category.

### 3. Backfill categories without blocking user actions

1. Create `services/api/scripts/backfill_shopping_list_categories.py` by following the dry-run/`--apply` structure of `backfill_shopping_list_values.py`. It selects recipes whose component category arrays are missing, malformed, or misaligned and shopping-list items whose category is missing/invalid; batches their text through a new Gemini category-only helper using the same six-ID response schema.
2. On `--apply`, write only missing/invalid category values, preserving valid existing category IDs and every other component field. Commit per successfully processed record; log and skip each Gemini failure so a rerun resumes remaining work. The script’s default dry run prints every planned recipe/item update and makes no writes.
3. Run the script once after the schema deployment as an operational migration. New imports and additions must work before, during, and after this job: uncategorized rows render under `other` until backfilled.

### 4. Replace the flat shopping list with native-feeling category sections

1. Create `apps/mobile/src/screens/ShoppingListScreen/helpers.ts` for pure section grouping/flattening/category-order transforms and `ShoppingCategorySection.tsx` for the section header, add row, and completed rendering; keep `index.tsx` as screen orchestration. Derive each user’s visible section order from `preferences.shopping_categories`; route items assigned to disabled categories into that user’s `other` section without changing their persisted category. Render all enabled sections, including empty ones, because each section must expose its own add control.
2. Replace the single global add/footer model (`ShoppingListFooter.tsx`) with header-delimited category rows: a translated category title, active-item count, disclosure chevron, active items, the category-local `AddItemRow`, and (when enabled) that category’s completed rows. Tapping a header collapses/expands its entire category; persist this device-only disclosure map in AsyncStorage keyed by the active household ID so users retain their own view. Collapsed sections hide their add control until expanded.
3. Persist `show_completed_shopping_items` through `usePreferences` and show its translated Switch in the existing Shopping List settings card. When false, a newly completed row stays dimmed/struck through in its category for 10 seconds, then exits; when true, completed rows remain visible immediately below that category’s active/add area. Unchecking cancels a pending hide and restores the row to its active category. Keep the existing global, confirmation-protected Clear completed action; it clears every category.
4. Preserve drag ordering with the existing `react-native-draggable-flatlist`, using one flattened discriminated data model whose static category/add/completed entries never start a drag. From `onDragEnd`, derive the destination section and category-local ranks, then send the full active `category_orders` map. A row dropped into another enabled non-Other section changes that shopping-list item’s category; a drop that remains in the virtual Other section preserves each disabled source category. Require the destination section to be expanded before it can receive a drop.
5. Use the installed `react-native-reanimated` list transitions: `FadeInDown`/`FadeOut` plus `LinearTransition` at 200–250 ms for insertion, removal, and reflow; a short check-circle scale/fill and light haptic on completion; and the inverse on uncomplete. Gate nonessential entry/exit motion on the platform Reduce Motion preference, while keeping state changes and haptics correct.
6. Retain existing item editing, presence locking, swipe deletion, keyboard visibility, keep-awake behavior, accessibility labels, and global clear confirmation. Move any no-longer-used global-footer styles, callbacks, and imports rather than leaving compatibility paths.

### 5. Expose personal category configuration and translations

1. Add `apps/mobile/app/(tabs)/settings/shopping-categories.tsx` and a `ShoppingCategoriesScreen` under `apps/mobile/src/screens/` to display the dedicated route. Add a `Shopping Categories` navigation row under the existing Shopping List settings card in `SettingsScreen/index.tsx`; the new screen uses the current user’s `shopping_categories` preference, six translated rows, native switches, and drag handles.
2. Toggling a category removes/adds its ID from the ordered preference array; `other` is visibly on and disabled. Reordering changes the same array. Queue full-array preference writes so rapid toggles/reorders commit in local action order, and roll back to the last confirmed server configuration on an error. These settings affect only the current user’s rendering and Gemini never depends on them.
3. Add every new user-visible label — category names, category screen/title/description, completion visibility, and category picker/add-item accessibility text — to `packages/shared/src/locales/en.json`, `pl.json`, `de.json`, `fr.json`, and `es.json`. Category IDs remain the only values crossing API/Gemini/storage boundaries.

## Critical files & anchors

- `services/api/src/api/models.py` — add validated category fields to persistence, API schema, and Gemini response models.
- `services/api/src/api/routes/shopping_list.py` — category-local add/toggle behavior, atomic cross-category ordering, and the shared-list snapshot.

- `packages/shared/src/hooks/useShoppingList.ts` — optimistic category-aware cache updates and ordered-write serialization.
- `apps/mobile/src/screens/ShoppingListScreen/index.tsx` — replace the current one-list/global-footer renderer with collapsible category sections and motion.

## Assumptions & contingencies

- The project’s startup `ALTER TABLE ... IF NOT EXISTS` migration pattern remains the deployment mechanism; if an Alembic migration system is introduced before implementation, express the same defaults and non-null guarantees in one migration instead.
- Gemini categorization failure during a new import/backfill must not block recipe/list use: preserve a valid prior ID, otherwise use `other`, log the failure, and let the retryable backfill repair it later.
- Cross-category drag is limited to expanded, enabled destination sections. A disabled category’s rows are visually merged into Other but retain their stored category until explicitly moved to a visible category.
